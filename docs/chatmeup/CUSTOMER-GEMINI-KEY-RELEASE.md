# Customer Gemini credentials — release gate
This is an unactivated backend source batch, not an enrolled customer service. No real keys were collected. The existing operator Gemini pool stays untouched. Customer credentials are isolated per account, AES-256-GCM authenticated with tenant/user scope, and validated via one bounded fixed-content generation before storage. A dedicated 32-byte deployment secret is mandatory; never generate a random fallback on each boot. A failed probe preserves a prior verified key; deletion fences in-flight enrollment; account disablement clears the credential.
Before composition: inspect the authenticated strategy boundary (the inference envelope intentionally strips IDs), call relay, Live, reply TTS and emergency service separately. Customer credentials must never be selected for unrelated users, quota circumvention, platform background work or emergency reporting. Implement identity-bound selection and provider-mode tests, real PostgreSQL concurrent save/remove/deactivation tests, key rotation and deployment secret handling, age and regional controls, informed consent and provider terms review. Do not expose enrollment HTTP routes or request actual customer credentials until this is qualified. Platform service can continue without customer keys. No reward or political metric may depend on providing a key.
