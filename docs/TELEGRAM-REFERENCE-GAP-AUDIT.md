The branch also contains an explanatory [index](https://github.com/Baatiku/Masanawa/blob/04a543b0886683ce0efa8bebfc95af7c1c05fe9b/telegram-decompiled/TELEGRAM-COMPONENTS-INDEX.md) and a [preliminary benchmark](https://github.com/Baatiku/Masanawa/blob/04a543b0886683ce0efa8bebfc95af7c1c05fe9b/docs/TELEGRAM-WALLET-AND-P2P-BENCHMARK.md).
- **NOT in committed reference:** classes.dex/classes3.dex/classes4.dex, decoded Java/Kotlin, executable wallet engine, Mini App HTML/JS, backend escrow logic, database rules, API trace, runtime screenshots or instrumented session recordings. The README/index *describe* WalletEngine2, WebViews, seed phrases, transaction phases and P2P details, but they are **secondary claims without a matching inspectable binary/source** in this branch. Do not label those as direct decompile verification.
- **External product documentation** corroborates Telegram Mini App navigation, contextual launch, invoice UI, biometric/haptic/lifecycle APIs: [Telegram Mini Apps](https://core.telegram.org/bots/webapps) and [client integration](https://core.telegram.org/api/bots/webapps). It does **not** establish the exact P2P backend, fiat payment rail coverage, transaction latency, wallet custody implementation or current regional availability in this bundled APK.
- **Independent upstream verification path:** Telegram publishes its [official Android source](https://github.com/DrKLO/Telegram) and [app/source/licence guidance](https://telegram.org/apps/) (GPL-2.0-or-later for Android). A version/tag-aligned comparison against that source may resolve class and UX questions more reliably than asset-name inference. The exact v13.1.0 commit and custodial @wallet Mini App backend were **not** matched or audited here; GPL obligations and branding restrictions apply if source is reused, so prefer independent implementation of observed design patterns.
- **Reference resource != implemented feature.** A model named secureid_ocr_nn.dat is evidence of a packaged OCR asset, not evidence that Telegram or Masanawa grants KYC approval via OCR. Card textures indicate the possibility of animated visuals, not proof of gyroscope logic. Currency JSON contains payment-oriented min_amount/max_amount fields; those values are **not** Masanawa limits or exchange quotes.
- **Corrections to the preliminary benchmark:** its Windows file:/// links are nonportable; “settles within 100 milliseconds”, “fraud-proof escrow”, exact 15-minute timer, all listed bank rails, encrypted order chat and precise native class/function claims are **unverified by these uploaded bytes**. Use configured authoritative deadlines, never promise fraud-proof settlement; never treat screenshot or “I paid” as release proof. The dual custodial/seed-wallet narrative is **not** an instruction to create a second wallet in Masanawa. Do not import Telegram wallet textures, icons, theme files, code, fonts or models into our shipped app without rights, security and licensing reviews.

**Status labels below:** **EXISTS** = matching Masanawa source identified, not end-to-end accepted; **PARTIAL** = existing path with missing/unfinished acceptance; **UNVERIFIED** = no proof either way from bounded source audit; **NEW** = distinct proposal, not an assertion that every repository file was scanned. **P0** = complete existing critical journeys; **P1** = worthwhile next product increment; **P2** = optional; **NO** = do not adopt.

## C. Consolidated user journeys and new UI surfaces (do not introduce new root tabs)

**Shared states for every surface below:** initial skeleton; truly empty with next action; partial data vs zero; typed retryable service/network error; offline cached/read-only (never offline payment authorization); expired session and wrong-account cancellation; permission-denied manual alternative; slow/unknown provider outcome bound to original ID; small-screen/RTL/200% text/TalkBack; back restores permitted draft before submit and **resumes authoritative status** after submit. Destructive/money actions require explicit confirmation, no automatic model action.

1. **Chats → human thread → attachment Pay / recognized account number → existing Wallet Send (WLT04) → shared review (WLT07) → status & receipt → return to thread.** Controls: choose owned eligible asset, recipient from server-bound identity, exact amount/fee, optional note, Cancel/Confirm and Review. Only after verified receipt linkage may both users see properly scoped chat cards. Tap card → WLT10 detail/help. Forged link and copied receipt cannot imply settlement. Chat context is never passed to an AI spending authority.
2. **Wallet → portfolio (WLT01) → P2P (WLT08) → Buy/Sell offers → filters and merchant profile → offer detail → order confirmation (WLT09).** Show asset and actual network/custody capability, fiat denomination, rate, min/max, remaining, payment rails permitted in region, seller identity verification and qualified reputation. Order creation reserves assets atomically; display spinner, durable request reference and retry status rather than create a duplicate order. Region/identity/insufficient reserve screens explain disabled actions.
3. **P2P order (WLT09) → payment details and deadline → paid claim → seller independent check → release or dispute → WLT10 receipt.** Participant-only order chat/evidence drawer may attach contextual messages. Controls: copy verified payee/bank/amount, open evidence, mark paid, report issue, refresh server status, cancel only if allowed, confirm verified receipt for seller. Escalated staff actions require independent authenticated authority; buyer claim, screenshot and timer cannot release holdings. Paid/disputed orders remain reserved until an authorized resolution. Resume across app restart, push and account switch.
4. **Wallet → owned asset detail (WLT02) → internal deposit address/request OR blockchain deposit OR Withdraw/Swap (WLT03/05/06) → WLT07.** Address/network/memo/fee/expiry are accurately scoped; verification, underpayment and reorg lead to recoverable status. No second seed wallet, no forced MSNW conversion, no fiat balance from valuation.
5. **External Android Share → authenticated target picker → authorized chat/Room/Status draft → media preview/edit/cancel → confirmed upload and message status.** Share targets are not bill payments, and receiving share intents never initiates a Wallet transaction. Denied storage/camera permission leaves file selection fallback where applicable.
6. **Notification → lock-screen-safe preview or protected Quick Reply → reauthorization if required → thread, with correct back-stack.** Clear expired or prior-account pending actions, throttle repeated notification taps, retain no confidential message content in widget storage.
7. **Settings → Security → passkey enrollment/revocation (conditional) / two-step recovery → test login + financial step-up separately.** Biometric convenience never replaces server-side spending approval. Account recovery revokes device sessions, and no seed phrase is requested.
8. **Chats/Rooms → opt-in home-screen shortcut/widget**, showing name/count without sensitive text by default. Launch after account authentication; revoked membership/account switch displays neutral empty state.

## D. Contracts, architecture and safeguards

- **No alternate ledger.** Extend canonical multi-asset custody contract: asset ID + issuer/contract + network/custodian representation, atomic unit precision, available/reserved/total, approved operation capability, quote source and version. Escrow reserve/release/refund and provider compensations are balanced, idempotent and authorized. Marketplace is an overlay on that authority, not a new wallet product.
- **Chat payment events** must contain only operation ID/type, involved actor IDs, asset ID, display-safe amount, participant-scoped status and privacy-safe receipt deep link. Chat is a projection; canonical financial status comes from Finance. Outbox/delivery deduplicates by unique operation and authorized recipients. Never let a notification/chat event *become* the ledger event.
- **P2P merchant/order API** should return policy-derived eligibility, verified method ownership, immutable quote ID/version/deadline, seller reserve reference, participant roles, sufficient-sample reputation, order status/version, evidence ACL, reviewer audit and receipt ID. Enforce state transitions and compare-and-swap/version under two-device concurrency.
- **Permission surface:** MIME shares URI grants scoped to target and cleared on account change; lock-screen replies short-lived and user-bound; contact import explicit and revocable; ML/identity processing requires genuine user consent, limited retention and a validated provider. No untrusted bot WebView bridge to unrestricted storage, payment approval or PII.
- **Navigation:** reuse five_tab_shell.dart, wallet_screen.dart, wallet_flow_page.dart, msnw_p2p_screen.dart, human_chat/screens.dart, core/shell_deep_link.dart and existing settings routes. Client feature flags reflect *server* capability; hardware permission prompt occurs at point of use only.
- **Benchmarks vs guarantees:** performance, timed orders and 3D appearance are UX candidates, not verifiable service guarantees from these files. Financial regulator/provider contracts, country permission and settlement proof govern actual activation. No Telegram proprietary implementation/assets transplanted.
