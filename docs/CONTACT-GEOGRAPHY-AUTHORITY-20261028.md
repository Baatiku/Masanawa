# Contact geography authority — 28 October 2026

This is **private self-declared contact metadata**, not residence, GPS, verified phone ownership, public profile data, ad consent or financial/data provider admission. Email OTP continues to authorize new sign-ins. Existing Nigerian-local contact records remain readable with `legacy_phone_hint`; no state/region is inferred for them.

## One versioned source, two generated consumers

- Canonical checked-in source: `data/contact-geography.v1.json` (45 explicitly supported countries, each with ISO 3166-1 alpha-2 code, calling code and ISO 3166-2 subdivisions). Its declared version is `iso-codes-4.20.1-libphonenumber-js-1.13.15-v1`.
- ISO snapshot: Debian's maintained [`iso-codes`](https://salsa.debian.org/debian/iso-codes) release **4.20.1-1**, Git commit `0ca8260` (1 January 2026). ISO data is redistributed with upstream attribution under [LGPL-2.1-or-later](https://salsa.debian.org/debian/iso-codes/-/blob/master/LICENSES/LGPL-2.1-or-later.txt); the derived canonical JSON remains available in source. The snapshot records SHA-256 hashes for both upstream ISO JSON files. Calling codes are generated through pinned `libphonenumber-js/max@1.13.15`, the same parser that validates E.164 in the Gateway. This is a pinned registry, **not** a claim that metadata updates happen automatically.
- Run `node scripts/contact-geography.mjs --iso-source PATH_TO_PINNED_ISO_CODES_CHECKOUT` to deliberately refresh the canonical source from the upstream `data/iso_3166-{1,2}.json` files. Updating versions/commit/hashes is a reviewed change. Run `node scripts/contact-geography.mjs` to generate both app and Gateway outputs, or `node scripts/contact-geography.mjs --check` to prove they match the committed source. CI's source tests also verify generated country, calling-code and subdivision parity.
- Generated runtime consumers: `apps/mobile/assets/contact_geography.json` and `apps/mobile/lib/src/core/phone/country_contact_generated.dart` for signup and private Account Data, plus `services/gateway/src/country_contact_generated.ts` for authoritative server validation. Do not independently edit country maps in those consumers.

## User flow and safeguards

1. The first-signup email-OTP details screen suggests a country from a non-permissioned locale, leaving the picker editable. The dial prefix is displayed once, outside the national-only text field. Pasted `+`/`00` numbers are parsed into the national text and one combined E.164 model; an ambiguous `+1` must be confirmed as Canada or the USA by the person.
2. A country change clears the old state/region. The bundled registry works offline; if unavailable, the form blocks submission and offers retry. An ISO country without listed subdivisions has an honest unlisted path; no region is guessed from a phone number.
3. The Gateway uses maintained phone metadata for normalized E.164, rejects actual country mismatch even for shared calling codes, requires a selected subdivision where the country has a list, and checks subdivision *membership* against its generated ISO snapshot. This is not proof that the number belongs to the person. The email OTP credential stays separate.
4. The private Profile/Account Data GET and PATCH are authorized, `no-store` and account-epoch fenced. After a PATCH—including a lost response—the client reads the private record back to determine whether the write committed. Identical repeated writes do not advance the PostgreSQL profile's `updated_at`. Existing non-E.164 legacy NG contacts are permitted only as compatibility reads; no fabricated subdivision.
5. None of these fields are promoted into public Masana/profile projections. No geotargeting, foreign wallet funding, foreign mobile-data admission or provider switch is enabled by this work. Account-deletion/legal-hold policy remains governed by the separate deletion lifecycle rather than any hidden signup inference.

## Verification

Gateway source/API checks exercise +234 and local trunk 0, `00` paste, shared +1 country mismatch, incorrect subdivision membership, invalid/long/short inputs and no subdivision. Flutter checks cover the pinned offline asset, version/country mismatch, prefix separation, ambiguous paste, country edit, Hausa/RTL/large text and private Profile session-fenced readback. PostgreSQL integration requires `MASANAWA_TEST_DATABASE_URL` and checks persistence after repository restart, legacy provenance and idempotent repeat writes. Test failures or missing hosted Flutter/DB gates must keep corresponding acceptance boxes open. Changes here must never turn on provider-country funding or advertising choices.
