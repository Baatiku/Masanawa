# Status public visitor, guest proof and referral privacy — source policy

**Status: partial, feature-gated implementation; not an approved live privacy notice or guest-view launch.** Owner checklist: `SPE-B01`, `B05`, `B07`, `B10`, `B11`, `B12`, `B14`. The canonical 88-item checklist remains the source of truth. No public/financial/reward gate may be enabled by this document.

## What the current source actually does

- An anonymous `/status/:postId` GET serves a cache-disabled, HTML-escaped, JavaScript-free public text/image preview only if the source is approved and eligible. Its optional thumbnail is a server-normalized, rights- and alt-reviewed platform image; signed private-object URLs, tenant IDs, account IDs and viewer IDs never appear in the document.
- The public page issues no view challenge, cookie, advertising pixel or reward. No guest qualified-view collection or payout currently exists. Server infrastructure can still create standard security/access logs; their storage/retention is deployment-specific and **not yet certified**.
- If the original sharing link is still valid, the page explains its opaque referral code and offers two separate choices: open with original-sharer attribution, or open the canonical post without it. Refusing referral attribution cannot itself become a referred charge. A forwarded token cannot change its original signer.
- Authenticated app views use a keyed HMAC digest of tenant plus authenticated user, never a raw viewer ID in the `feed.qualified_views` record. A server-clock challenge must have at least six seconds elapsed before the server can consider client foreground/visibility/engagement assertions. Those client assertions are **not independently fraud-proof**; reward issuance and financial admission stay OFF.
- Unclaimed view challenges older than 24 hours are pruned by a bounded, restart-safe, account-independent maintenance sweep. This does not touch charged/claimed challenge rows, immutable financial ledger operations or the unique-view evidence needed to prevent duplicate payment. Financial/audit retention requires a separate approved period, basis, lawful access/deletion review and reconciliation policy; do not imply that ledger evidence is erased on an ordinary page close.

## Guest qualification design gates before any activation

1. Obtain jurisdiction-/age-appropriate review for web guest measurement and attribution. Explain purposes, pending commission and how to decline; optional advertising measurement must not be bundled with access to public post content.
2. Implement an explicitly consented, first-party, short-lived, cryptographically random guest session and signed server challenge. Never use device fingerprint, contact upload, cross-site cookies, geolocation inference or a raw IP address as an identity key. A carrier/shared mobile-data IP must not suppress another person's legitimate view.
3. Require real page foreground and continuous 50% visibility for at least six seconds with a renewed engagement signal, then submit an abuse-resistant signed proof. The server owns uniqueness/financial settlement; a browser clock, link fetch, prerender, crawler, hidden tab, autoplay or refresh cannot charge by itself. Browser signals are not proof of a distinct person, so use conservative risk holds, fraud review and tested false-positive protection.
4. For app/web transitions, bind the web guest proof to an authenticated viewer only with a clear consented handoff; prevent double billing across the transition, clearing a session, sharing another link or overlapping boosts. Do not infer real identity from IP or fingerprint.
5. Specify and enforce bounded retention for guest session secrets, discarded proofs, network risk evidence and any optional analytics; support consent withdrawal and authenticated deletion while preserving only narrowly required audit/financial evidence. Document processor/CDN/access-log retention separately and implement monitored deletion/retry.
6. Add external browser, no-JavaScript, consent-refusal, accessibility and full fraud/reversal/settlement tests; obtain provider/economic qualification before any whole-MB reward becomes spendable. Maintain customer-traffic kill switches and incident rollback.

**Release decision:** Guest views are nonpayable and uncollected in the current public route. A reviewed policy, authoritative proof implementation, real cross-surface tests, provider backing and staged monitoring are blockers for checking `SPE-B01/B07/B10/B12/B14`, not a reason to switch on a fake analytics or rewards path.
