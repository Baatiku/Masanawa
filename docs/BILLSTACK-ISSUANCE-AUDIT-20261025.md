Official [reserved-account creation](https://billstack.gitbook.io/api/reserved-account/create-account) specifies `POST https://api.billstack.co/v2/thirdparty/generateVirtualAccount/`, Bearer secret, reference, email, phone, firstName, lastName, one bank per request, and a single returned account. It documents both `9PSB` and `PALMPAY`. The adapter now accepts either provider-confirmed bank, persists the returned bank ID and displays it to the customer. New requests default to `9PSB`; `MASANAWA_BILLSTACK_BANK_ID=PALMPAY` opts new requests into PalmPay without changing assigned accounts. The [reserved-account overview](https://billstack.gitbook.io/api) says the number persists for a customer. The [webhook payload](https://billstack.gitbook.io/api/webhooks) identifies `PAYMENT_NOTIFICATION`/`PAYMENT_NOTIFIFICATION`, `RESERVED_ACCOUNT_TRANSACTION`, a transaction reference, original merchant reference, receiving account and amount. The owner supplied an actual PalmPay dashboard sample with numeric naira amount and additional `wiaxy_ref`/`transaction_ref`, payer and customer fields; tests reproduce that structure with anonymized values. The sample did not show signing headers or prove finality. Billstack's [current website](https://billstack.co/) also advertises *one-time checkout accounts*, so the merchant must confirm that the provisioned product/key is the persistent reserved-account API before enabling issuance. Its published HMAC example agrees with `x-wiaxy-timestamp`/`x-wiaxy-signature-256` and SHA-256 of `timestamp.rawBody`; the repository test is simulated and cannot prove the live dashboard sends this contract.

## Missing end-to-end authority

- [x] **New mobile signup identity source:** email OTP proves the email; first and last name plus a Nigerian contact phone are required before creating a new email account. The phone is stored separately and prefills Data redemption, where it can be edited. It is not a phone login credential or phone-possession proof. The mobile no longer offers phone signup; legacy password endpoints remain for existing-client migration and need an explicit cutoff plan.
- [x] **Existing-user completion source:** Fund NGN now shows an authenticated first/last/contact form when an existing email account lacks applicant fields; Gateway accepts the update only while no Billstack account has been started. Assignment and funding availability are separate states. The contact becomes the Data default after the session next refreshes from the server.
- [ ] **Phone proof:** Billstack's published create request requires a phone number but does not state possession verification. If its merchant policy requires a verified phone, qualify an OTP binding before live transfers. The 500 MB welcome remains unavailable without its separate verified-phone eligibility proof.
- [x] **Automatic initial attempt:** after a new email signup's session is persisted, mobile calls `POST /v1/gb/wallet/virtual-account` once. Gateway reads the stored applicant fields, durable pending reference and provider 9PSB response. Issuance may proceed while funding credit remains disabled. Viewing the balance card makes no provider write.
- [x] **Pre-dispatch recovery:** if the mobile attempt was interrupted before the Gateway claimed a reference, Fund NGN offers Get funding account when assignment is available. The authenticated GET distinguishes applicant completion, assignment availability and funding-credit readiness.
- [ ] **Post-dispatch recovery:** a timed-out provider write leaves a pending reference that must be reconciled, never blindly replayed. Confirm an official reference lookup/recovery API or an operator procedure. Test actual Billstack account entitlement, exact returned account, crashes and restart.
- [ ] **Provider product and applicant eligibility:** confirm the provisioned key permits persistent reserved accounts for the selected bank, required KYC/no-BVN policy, sandbox/live mode, fees, limits, name/phone formats and account availability with Billstack. The production applicant reads a verified-email profile; phone possession is not yet verified.
- [ ] **Independent settlement and reversal:** obtain Billstack's documented lookup/final-status API and refund/reversal notification contract. The existing webhook validates a signed raw message and account/ref/kobo, then requires an independent `billstackSettlementVerifier`; production does not implement that port, so it cannot credit. Reversal debt/freeze journal exists internally but lacks a qualified event adapter. Test real provider duplicate, delayed, under/overpayment, reversal and lost webhook, with a real reserved account and small controlled deposit. Never treat a signed notification alone as final funds.
- [x] **Custom-domain routing:** owner added DNS; Railway reports ownership verified and certificate valid. The current production gateway deployment follows GitHub `main` and passed Railway's `/readyz` deployment health check.
- [x] **Webhook reachability:** the owner saved the custom-domain URL in Billstack; its dashboard and Railway HTTP log both confirm HEAD 200 after PR #455 deployed. No payment was created by this probe.
- [ ] **Provider operations:** qualify the actual signed POST headers, independent finality and reversal contracts before accepting real payment notifications. Then test real callbacks, rollout/migrations, historical callbacks, client cutoff, monitoring and reconciliation. The handler rejects unqualified notifications rather than acknowledge or credit them. The supplied sample used an older `REF-...` merchant reference and must not be imported or credited into a newly generated `gb...` account. Railway credentials are names only through the connected read tool; do not copy secret values into source or logs. `MASANAWA_NGN_FUNDING_VERIFIED` should remain off until all gates pass.

The compact Wallet/Send/Data card contains both balances and an account number when assigned. It never presents an unassigned number as a real bank account. No APK or Flutterwave fixed-IP hosting work is part of this audit.
