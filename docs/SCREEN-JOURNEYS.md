## Required golden end-to-end journeys
1. **New user:** install APK → select language → register/sign in → Chats → discover Masana → message → record voice → receive answer → leave/reopen → no lost state.
2. **Call:** chat → start call → authorized billing/mic → speech both ways → network interruption/reconnect/hangup → accurate history/settlement.
3. **Creator:** public profile → one free Masana → generated preview → publish → discover from second account → follow/chat → pause → visibility revoked.
4. **Creator paid:** second Masana quote 5,000 MSNW default → exact single-use confirmation → charge once → publish → receipt; insufficient balance and replay do not publish.
5. **Room:** discover → join/subscribe (if qualified) → ask/receive → leave/rejoin → correctly recover permissions.
6. **Status:** discover/follow → audio post → background/foreground → comment/report → protected creator identity.
7. **Wallet:** multi-asset portfolio → asset/network deposit → confirmed credit → internal Send with no chain submission → external Withdraw with exact fees/status → in-Wallet Swap → canonical history, quantities and covered portfolio estimate (WLT01–WLT10).
8. **P2P:** approve merchant offer → escrow → buyer marks paid → seller confirms or disputes → authenticated release → ledger/alerts/receipt; negative replay, expiry and concurrent release.
9. **Bills:** Wallet or Gwani → catalog with current price → correct recipient → authorize → provider receipt → ledger readback; timeout/retry cannot double-buy.
10. **Account switch:** after chat, push, creator tools, Wallet, P2P and Room use → switch account → none of prior account's private data or old async results appear.
11. **Recovery:** restore PostgreSQL/object copies off-account → schema/ledger/custody consistency → protect old liabilities and prevent unauthorized overwrite.
12. **Global market:** locale/RTL/low data + payment region eligibility → show only supported operations; unavailable is explicit and never fabricated.

### State contract applying to every H/R route
- **Loading:** compact list/profile skeleton; retain permitted cached content during refresh. Don't block first paint on contacts/provider discovery.
- **Empty:** Humans “Find someone to start a conversation”, joined Rooms “Create or discover a Room”, search “No matches”; one useful action. Empty creator sections are omitted.
- **Error/partial/stale:** inline failure with Retry; retain already loaded authorized rows but label refresh failure. No fake empty list or fake available call. Operation uncertainty reloads authoritative state before replay.
- **Offline:** label connection state, retain read content/drafts; sends show pending/failed accurately, never delivered without server evidence. Failed writes reuse durable client IDs. Do not queue financial or membership permission changes blindly.
- **Permission:** optional contacts matching, microphone prompt only on record/call; Denied → explanation/settings/retry, username search/text stay usable. Private Room and blocked-profile denial never reveals restricted content.
- **Account switch:** clear contact search/selection, profile follow overrides, old page data, drafts/media URLs/recordings/call session; cancel or generation-fence async completions. Push/deep link reauthorizes against current account.
- **Accessibility:** 48dp targets, semantic tab/action/voice status labels, 320px width/200% text, keyboard avoidance, RTL directional layout, sufficient green/white contrast, accessible audio controls. No horizontal clipped action rows.
- **Back/deep links:** routed entry preserves tab/list/draft; unauthenticated link resumes only after correct account auth and authorization; missing/revoked targets show unavailable with return action.

### Canonical contracts and end-to-end acceptance
- Contacts initial API: authenticated `GET /v1/profiles/contacts?q=<public search>&after=<handle>`, fixed page size 30 (pagination, not a product contact cap); blank query lists followed public humans and accepted-conversation peers. Stable ascending handle cursor. Only handle/name/bio/avatar summary returned; tenant/current user derived from auth. Literal case-insensitive name/handle search, self/inactive/moderated/bidirectionally blocked exclusion. No arbitrary client tenant/user scope or phone lookup.
- Reuse `talks.public_profiles` and owner edit/follow APIs. `GET /profiles/:handle` and by-user variant must enforce the same active/block/moderation boundary; self may still inspect/edit their own profile. Public creator Masana comes from the existing active/published server directory keyed by creatorHandle; not an independent untrusted profile array.
- Direct chat: typed conversation target (`human` vs `masana`), participant-only durable thread/pair/request IDs, scoped media and receipts, deletion tombstones; server owns sender, delivery and request state. Separate human transport prevents accidental model requests/billing.
- Calls: explicit human peer identities, short-lived participant media tokens and authoritative signaling transitions; ring/reconnect/teardown idempotency. No human call passed through Masana paid voice flow.
- Rooms: extend existing room/membership schema and APIs with roles/visibility/posting permissions/participants; delete retired Rooms records/history and start the redesigned product empty. Jobs recheck membership/agent activation at execution time; mention default, automatic publishing only by owner setting. Models cannot authorize financial actions.

## Multi-asset Wallet contract — owner clarification, 21 October 2026

This is the current Wallet design authority. It replaces MSNW-only home, combined Send/Receive and duplicate crypto-wallet navigation. MSNW is the platform service asset; users also hold each individually supported token. Asset symbols are not network/contract identity. Holding fiat currency is not implied by displaying fiat estimates or accepting a fiat purchase. Funding, internal transfer, withdrawal, swap and marketplace availability are separately server-controlled. No automatic conversion through MSNW. Existing platform services may quote MSNW, but holding another token never silently authorizes its sale: offer an explicit qualified Swap and return to a refreshed service quote, or explain insufficient MSNW. No mandatory wallet setup to access free communication.

### Portfolio math and asset identity

- Default estimate is NGN for initial Nigeria onboarding; user may select a server-supported display currency. Show “Estimated portfolio value”, not a fiat cash balance. Exact token quantities remain primary in each asset row. Changing display currency never trades funds.
- For each unique owned custody claim: **settled total = available + reserved**. Reserved withdrawal, P2P escrow or approved spend remains owned and is counted once until the definitive debit/transfer. Pending uncredited deposits and disputed/reorg-unverified receipts are shown separately, not as spendable or owned confirmed holdings. Do not count custodian backing or an on-chain mirror again as another user holding. Canonical journals determine when ownership changes.
- Estimated portfolio value sums priced settled totals using authoritative asset/display-currency rates, exact decimal math and defined timestamps. If any holding is unpriced, stale or balance-unavailable, label “Partial estimate” with coverage and excluded assets; preserve last verified values labelled stale or show unavailable. Never label a subtotal as complete, silently exclude an asset, assume a stablecoin peg, treat unknown as zero, or value MSNW from its name: use versioned 1 MSNW/NGN policy and real FX for foreign estimates. If nothing is priced, show valuation unavailable while still displaying quantities.
- Canonical asset ID includes the actual issuer/contract identity; backing lots include network/custodian domain and precision. Only proven fungible redeemable representations can aggregate to one row, with network breakdown. Bridged/wrapped/unsupported representations remain distinct; identical tickers do not authorize merging. If cross-network internal transfer would need a bridge/conversion, require an explicit qualified quote or reject it. Internal transfers move ownership in the same qualified custody pool without a chain transaction.
- Inventory must come from authoritative owned balances plus supported asset metadata, independent of which deposit routes are enabled. Independent flags for hold/deposit/send/withdraw/swap/P2P, disable reason, network health, limits and verification requirements govern actions. Disable a deposit rail without hiding existing holdings. Refresh failure for one asset must not erase the others.

### Deposit and withdrawal details

Deposit address/invoice creation does not credit a balance. Use chain/provider ownership attribution, token/network match, verified confirmations, callback deduplication and reconciliation. Bind credited amounts to actual verified received amounts and disclosed fees; a client-requested amount is not settlement proof. A reusable address is displayed only if supported; otherwise explain exact amount, invoice expiry and repeat-payment behavior. Always display a required memo/tag beside the address and encode it correctly for chain QR. Include address/network warnings, minimum/net-credit conditions, copy/share and accessible manual alternatives. Expired/late/underpaid/overpaid/wrong-chain deposits enter documented recovery; do not promise recovery where impossible or issue credit without proof.

An external withdrawal reserves exact source funds/fees under one original reference before provider submission. Persist and recover across restart; unknown submission cannot start a second payment. Distinguish queued, awaiting approval, submitted, confirming, completed, failed/refunded and manual review from actual authority. Cancellation is offered only before the irreversible boundary and if the backend can honor it. Definitive failure releases/compensates exactly once; late success/reorg requires canonical reconciliation. Fee changes or destination/network/tag edits require a new quote and approval. No platform private keys or seed phrases are collected by this custodial flow.

Existing provider-based crypto Deposit asks for an amount and creates an invoice; retain this adapter behavior honestly until reusable addresses are qualified. Existing MSNW conversion accepts an external address and pays out crypto; reuse its quote/recovery authority through an explicitly labelled conversion-and-withdrawal adapter, not a second generic withdraw UI or a pretend in-Wallet swap. It must not make withdrawing an already-held asset depend on converting MSNW.

### P2P balance and payment rules

P2P uses the same asset authority, no separate Funding/Trading wallet and no manual balance transfers between products. Listing an offer does not create holdings; atomically reserve required seller inventory at the server-approved order boundary and prevent overselling. Seller available falls and reserved rises; portfolio owned total remains unchanged except definitive fees. Release removes seller reserved and credits buyer available atomically with balanced fees/receipt. A permitted refund returns reserved to seller available. Buyer pending order is not a second owned asset. All participants see the same authoritative order status.

Fiat currency in an offer is the external payment denomination. Buying/selling tokens for a counterparty payment is not direct platform fiat withdrawal and does not create an in-app fiat balance. Protect payment details for admitted participants; verified payment method ownership, seller release authorization and audited dispute resolution remain required. Screenshot, buyer paid flag, push event, elapsed timer or AI message cannot prove payment or release escrow. Handle late payment, paid-before-expiry, disputed timeout, duplicate confirmations, counterparty cancellation and reversal with the existing recovery/finance contracts. Reuse order receipts within Activity, with direct resume links from home.

### Reuse, account state and acceptance

Reuse WalletScreen as portfolio, the existing asset/provider transports, WalletFlowPage forms, custody recipient inquiry, step-up, canonical history/receipts and P2P authority. Refactor CryptoWalletScreen into the shared asset/detail/operation presentation; no additional root wallet and no second backend provider/ledger. Legacy Fund/Receive/Convert/crypto links resolve to the corresponding shared journey, preserving authorization and account ownership. Any external-Send alias opens Withdraw. Chain QR/request QR/profile QR have explicit different intents; a scanned address never authorizes a debit.

Signed-out/deep-link resumes authenticate and revalidate asset/recipient/capability. Loading, empty, error, unsupported, maintenance, stale, offline and permission-denied states explain the issue and preserve only account-authorized safe drafts. Process death resumes by original operation reference. Logout/session change clears private amounts, addresses, drafts/caches and rejects stale asynchronous responses. Partial outages do not become zeros. No background clipboard harvesting, offline spend queue or client-success-only biometric approval. Keep all forms scrollable at 320px/200% text/RTL; keyboard, focus, contrast and screen-reader labels cover amounts, fee units and status.

Golden qualification: (1) deposit USDT on an eligible network → confirmed held quantity/estimate; (2) Send part internally to another account → no chain submission and balanced custody; (3) withdraw remainder externally → correct fee/reservation/status; (4) Swap owned asset A into held B → both balances reconcile; (5) P2P buy/sell → same-Wallet reserve/release/refund; (6) unavailable network/rates, missing MSNW policy/FX, unknown outcome, two-device concurrency, fee changes, malicious QR, process kill and account switch. Source/unit/PostgreSQL/Flutter/device/provider/production results stay separate. No APK unless owner explicitly requests it.
