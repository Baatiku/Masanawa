# Masanawa WhatsApp AI Management Centre — linked-device architecture

**Owner decision, 18 November 2026:** Use ordinary WhatsApp linked-device QR pairing, **not** Meta Embedded Signup or WhatsApp Business Cloud API. Deploy to the existing Masanawa Gateway/Ops/Worker/PostgreSQL architecture. No separate user identity, balances or financial ledger may be invented.

**Important account limitation:** The `@whiskeysockets/baileys` transport is an unofficial third-party WhatsApp Web client. WhatsApp can revoke a link, require a new scan, change its protocol, or restrict accounts that use unauthorized automation. Unlike the official Business Platform, there is no guaranteed service-level support or connection lifetime. Do not use it for unsolicited bulk campaigns. A stable QR session store does not override WhatsApp's account decisions.

## 1. Components

| Component | Responsibility |
| --- | --- |
| Admin dashboard | Start a new phone slot, display live QR, reconnect/disconnect/enable/disable, configure role, voice, inbox, templates, human takeover, analytics and security test |
| Ops service | Authenticate every admin request with `whatsapp.read`/`whatsapp.write`; create number slots; render QR locally; read encrypted session status; save optimistic-lock assistant policy and audited templates |
| Canonical PostgreSQL | `security.whatsapp_channels`, `whatsapp_auth_keys`, `whatsapp_assistants`, `whatsapp_threads`, `whatsapp_messages`, `whatsapp_jobs`, `whatsapp_templates`, account links/grants and append-only audit |
| Bounded Worker | Manage a leased Baileys socket per connected number; persist changing Signal credentials with AES-256-GCM; inbound deduplication; Gemini conversation responses, audio transcription and voice-note synthesis; outbox sending; reconnection |
| Canonical Gateway | Existing authenticated Masanawa session, NGN wallet and Buy Data authority; WhatsApp account linking and ten-minute read grant; account-scoped Buy Data quote, confirmation, spending caps and status |
| Web `/whatsapp/link` | One-time code claimed only after actual Masanawa sign-in; explicit read grant/revocation, live Buy Data catalogue, fresh quote, unambiguous purchase confirmation and status |

`MASANAWA_WHATSAPP_MODE=linked-device`; **no** Meta app ID, business app secret, WABA ID, Cloud API token or `/webhooks/whatsapp` entrypoint. The QR is generated by Baileys inside the private Worker, encrypted in PostgreSQL for a short time and rendered to a local image by Ops. It is never sent to a third-party QR-generation website.

## 2. Transport and recovery

1. Authorized admin creates a slot; it defaults to `enabled=true` so no second activation step is required after pairing.
2. Worker claims a short renewable PostgreSQL ownership lease, starts one socket with its own Signal credential store and waits for QR.
3. QR updates are encrypted and expire after 55 seconds. Admin polls the private QR endpoint. On the phone: **WhatsApp → Linked Devices → Link a device → Scan**.
4. WhatsApp may force a socket restart after the QR scan. Worker saves credentials and reconnects using the same encrypted keys without asking the admin to rescan.
5. Incoming individual messages (including eligible LID addresses) are deduplicated by `(channel_id, provider_message_id)`, persisted and queued. No group/status automation or history import.
6. AI and human outbound replies pass through one durable outbox. Unknown send outcomes are marked `uncertain` and require reconciliation; they are not blindly retransmitted.
7. If the account logs out, the system erases invalid Signal keys, records `needs_pairing`, and requires admin Reconnect + fresh QR. Disconnect erases encrypted keys but preserves audit/history.

**Reconnect and restart recovery:** Disabling an assistant or the phone's automated replies does not delete its encrypted linked-device Signal session. The Worker drains queued credential writes on a normal shutdown. If a reply becomes due while a socket is temporarily `degraded`, its job stays pending and retries for a bounded 15-minute recovery window. If an outgoing send was rejected *before* WhatsApp dispatch, it can retry; if the external send was attempted but its outcome is unknown, it is held as `uncertain` and never blindly replayed. The Usage & delivery screen exposes pending, overdue, failed and uncertain job counts, plus the latest safe diagnostic code. A true linked-device logout or explicit administrator Disconnect requires new QR pairing.

Worker must be a single bounded managed service with leased sockets, not one browser process per phone. On the owner’s two-GiB pilot, memory/capacity qualification remains necessary before unbounded concurrent numbers or background jobs are started. `maxSockets` defaults to four in the bounded manager; larger requirements need measured hosting capacity.

## 3. Roles and security

The per-number roles are templates; *permissions are separate backend-enforced switches*. Level ceiling is validated when saving policies and on dry-run evaluation:

| Level | Example permissions | Additional authority |
| --- | --- | --- |
| 1 Receptionist | `greet`, `faq` | Public service information only |
| 2 Support | `customer_support`, `registration_guide` | Human escalation |
| 3 Account | `account_link`, `funding_details`, `wallet_balance` | Signed-in account link + explicit ten-minute `account.read` grant |
| 4 Sales | `data_catalog`, `data_purchase`, `transaction_status`, `receipts` | Existing authenticated Gateway quote/review/reserve/confirm/idempotency path |
| 5 Advanced | `advanced_actions` | Case-specific admin approval and tool registry |

**Never treat an incoming WhatsApp JID, contact name, quoted message, model response or phone ownership as Masanawa authentication.** The Worker can provide private read-only balances/funding details only if a verified account link and unexpired ten-minute read grant exist. It has **no direct wallet-debit capability**. For Buy Data, it directs an already-linked customer to `/whatsapp/link`; that screen requires a real Masanawa session, current approved provider catalogue, fresh price/versioned quote and explicit checked purchase authorization. The Gateway verifies per-number role and permissions, serializes immutable customer-specific idempotency approvals and caps WhatsApp-originated purchases at ₦20,000 per order/₦50,000 rolling 24 hours before calling the **existing** NGN purchase service. That service performs canonical wallet reservation, provider dispatch, reconciliation and refunds. Confirmed delivered orders queue a WhatsApp receipt and appear in number-level sales analytics. A pending provider response is never represented as success.

## 4. Voice, instructions and automation

- Every number has separate assistant name, personality, greeting, English/Hausa language, text/voice/transcription preferences, Lagos working hours, escalation keywords and role.
- Per-number response mode: `always` (immediate), `away` (30–3,600-second human-first delay) or `manual` (log chats but never queue AI replies). For Away, a genuine outgoing message from the linked WhatsApp owner cancels queued AI work; the send worker rechecks for a later human reply immediately before dispatch. Bot echoes are not mistaken for owner activity. Multiple unanswered customer messages are coalesced to the latest prompt. The configurable away introduction is rate-limited per conversation.
- Per-number returning-contact memory: each WhatsApp JID gets one private PostgreSQL conversation thread, recent public dialogue context (up to 24 messages) and an independently updated long-term summary every eight eligible customer messages. The summary preserves language preferences, prior general assistance and unresolved topics; it filters account, payment, credential, number and private-identity details, and never establishes wallet authority. Admins can disable conversation memory for a number.
- The Worker checks a normal WhatsApp phone JID against the canonical **verified** `security.platform_user_profiles.phone` field. It may personalize generic reception and offer an immediate signup link to an unknown contact, but does not automatically authenticate or link an account merely because the numbers match. `contact_phone` is explicitly unverified and is never considered a wallet identity. The recognized/unregistered hint is refreshed on later messages so completed signups are picked up.
- Existing Masanawa persona voice enrollment allows authorized speaker sample uploads, audition, consent and provider-reviewed activation. Saving a number's custom `voiceId` requires its matching ready persona enrollment.
- The text Worker includes a no-tools Gemini FAQ path with a bounded, public-service conversation history, greeting automation, server-defined account/Buy Data routing, and deterministic protection responses. Customer messages are not given to the model as wallet authorities.
- Eligible incoming audio is stored temporarily as an encrypted Baileys media envelope, downloaded on the active socket and transcribed through Gemini. Text and/or synthesized voice replies use separate idempotent outbox entries. Existing consented custom voice IDs or the configured Masanawa voice feed provider audio, which FFmpeg turns into WhatsApp Ogg/Opus voice notes. Voice uploads and audition use the existing Masanawa persona voice enrollment service. Provider credentials and a compatible account remain required for actual audio delivery.
- WhatsApp voice synthesis now follows the canonical Masanawa recorded-voice sequence: request Gemini 3 speech through Interactions, fall back to GenerateContent only for a definite 400/404 rejection, validate PCM/WAV output, and encode a push-to-talk Ogg/Opus note. A generation/encoding failure is recorded before any WhatsApp send and may be retried safely. Text output is queued independently, so an unavailable voice provider does not suppress an enabled text reply.
- Saved reply templates are per number and editable by an authorized admin; a user can invoke an enabled matching template via `/template-name`. No unsolicited bulk scheduler is enabled.

### Account identity boundary

WhatsApp account possession and a Masanawa login phone can match without proving the same current human controls both. SIM reassignment, stolen devices and compromised WhatsApp sessions are real account-takeover paths. Consequently, matching phones unlock **public** greetings, account-detection hints, support and signup; they do not unlock private wallet balances, virtual-account details or purchases. A registered customer confirms their Masanawa identity through the existing one-time account-link flow, with a separate short-lived read grant and purchase review. No password, PIN or OTP is ever solicited in the WhatsApp chat itself.

## 5. Required private configuration

Put these in the existing private DigitalOcean `/etc/masanawa/runtime.env` (not Git, public Cloudflare variables or browser storage):

```text
MASANAWA_WHATSAPP_ENABLED=true
MASANAWA_WHATSAPP_MODE=linked-device
MASANAWA_WHATSAPP_SESSION_KEY=<unique base64 of 32 random bytes>
MASANAWA_GEMINI_API_KEY=<existing provider credential>
MASANAWA_WHATSAPP_GEMINI_MODEL=gemini-2.5-flash
MASANAWA_WHATSAPP_TTS_MODEL=gemini-3.8-flash-tts
```

Use a *stable securely backed-up* 32-byte session key. Losing it requires rescan of all numbers; rotating it requires an explicit re-encryption job. Configure the existing operator's private capability grants for `whatsapp.read` and `whatsapp.write`. Deploy PostgreSQL migration before starting updated Ops and Worker. The Worker must be healthy and the admin phone must scan at least one live QR before any account can be called connected. No credentials are placed in repository code.

## 6. Release evidence and operational acceptance

Automated source tests cover SQL schema, immutable audit, encryption integrity, role permission denial, bounded routes and existing Gateway/Worker integration. Cross-service CI and deployment must use the same reviewed head. A real WhatsApp account must pair in a secure interactive admin session; verify QR rotation, force-restart, incoming text, outbound receipt, manual takeover, disable and logout/rescan. A library unit test cannot substitute for a live linked device.

Validation gates before claiming the system is operating for a real WhatsApp account:

- Multi-number reconnection storm and memory qualification on the actual two-GiB Worker host; increase socket limit only after measurement.
- End-to-end real-device voice-note transcription, consented custom voice preview, public text and voice response, real NGN account-link, live bundle purchase and provider reconciliation using test accounts.
- Actual QR pairing from the administrator's physical WhatsApp client, staging migration, production environment secret installation, deployment and rollback rehearsal.
- Privacy retention/deletion operations and observed provider/model inference-cost reconciliation before treating cost analytics as billing evidence.

**Fail-closed contract:** do not activate a financial mutation, unauthorized voice clone, or forged account access merely to make its UI switch look enabled. Feature flags and role switches are not equivalent to delivery receipts or authorization.
